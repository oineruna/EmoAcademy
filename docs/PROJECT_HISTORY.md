# EmoAcademy：開発の経緯・現在地・今後の計画

更新日：2026年9月12日

## 1. このプロジェクトで実現したいこと

Quizlet風の使いやすい学習プラットフォーム「EmoAcademy」を作り、学習中の表情・状態を分析する感情モニターを組み込む。将来的には、学習行動・進捗と推定された状態を扱い、学習やUIに関する実験にも使える環境にする。

開発は、ログイン画面のデザインから始まり、認証と公開、学習ダッシュボード、感情分析、別バージョンからの機能統合へと広がった。

本書は会話の経緯と判断理由を残す引き継ぎ資料である。各段階の正確な作業日やコミット番号は照合していないため、時系列は会話上の順序で整理した。公開環境の現在の正常動作や、全機能の完成を保証する報告書ではない。

## 2. 現在の重要な方針

- デザインの本命は「案A：Quizlet寄せ・現行本命」。確認済みのログイン画面、左メニュー、アイコン、配置を維持する。
- 別サイトからは主に機能を吸収し、EmoAcademyのUIに合わせて実装する。
- 学習ダッシュボードは左メニュー、中央の学習カード、右側の感情モニターで構成する。
- 感情モニターは教材や学習カードを隠さず、学習の邪魔にならないようにする。
- 背景は淡い青系で明るく、カードには丸みを持たせる。文字は大きめで、少し太い程度にする。
- フォントは英語にPoppins、日本語にNoto Sans JPを使う方針。日本語・英語の切り替えに対応する。
- ボタンのホバーや選択には控えめな反応を付ける。ページ読み込み時のスライドインや、過剰に目立つクリック演出は不要。
- 学生・教師のロールを扱う。途中にあった保護者の案は採用しない。
- 独自ドメインは当面使わない。Web公開、認証・保存、モデル処理は役割を分ける。
- 新しい科目別進捗UIは参考機能として保持する。情報量を増やして主役にする意図はない。
- 公開の依頼とローカル確認のみの依頼が時期によってある。次の作業で自動的にコミット・プッシュ・デプロイしてよいとは扱わない。

## 3. どういう順番で進めたか

### 3.1 ログイン画面の試作

既存の「After Class Modal.html」の背景、Quizlet風のフォント・色・配置、CodePenのAnimated Glassmorphism Login Formを参考に、複数のログイン画面を作るところから始めた。

10案から9番目を中心に調整し、その後は案数を減らして、左に大きな画像、右にガラス調フォームを置く方向へ絞った。背景の点線・ドット、画像の大きさとブラー、枠の幅、余白、文字サイズ、ボタンの反応を繰り返し調整した。

登録とログインの切り替え、ロール選択、パスワード表示・強度表示、ログイン状態の保持、ヘルプ・復旧を追加した。新規登録ではヘルプ・復旧を表示しない方針になった。

見た目が変わるたびに修正が入り、「確認済みのデザインを勝手に変えない」が後の統合作業でも重要な判断基準になった。

### 3.2 実際の登録・ログインと公開基盤

当初は既存デモのFastAPI認証・JWTなどが残っていたが、EmoAcademyの認証はSupabaseに寄せ、WebアプリはVercelに公開する方向へ進めた。プロジェクト名もQuizroomなどからEmoAcademyへ整理した。

SupabaseのURL・公開キー、Googleログイン、認証後の戻り先、プロフィールとロール、SQLによるテーブル作成を扱った。Googleプロバイダーが無効なエラーや、PKCEの検証情報が見つからない問題も発生した。

確認メールが届かない問題ではResendを検討したが、独自ドメインを購入せず、メール確認なしで登録を試す方針を取った。その後、ユーザーからログイン成功の報告があった。現在のメール確認設定は別途確認が必要。

### 3.3 ログイン後をQuizlet風に統一

ログイン後の画面を、左サイドバーと丸い学習カードを中心とした構成へ変更した。「続きから始める」、学習グループ、質問・先生の回答などを整理し、不要な通知アイコンや重複した導線を減らす方針にした。

フォントはQuizletのHurmeを調べた後、無料の代替を検討し、PoppinsとNoto Sans JPを採用する方針になった。日本語・英語の切り替えも追加対象とし、認証メッセージの言語混在も修正対象にした。

### 3.4 別バージョンを確認し、機能を統合

Downloads内やEmoAcademy内の「learning1-emotion_detection-main」を参考に、別バージョンの画面をローカルで起動して確認した。過去の会話には「learning1-emotion\_detection-main」という表記もあり、操作前には実在するパスを確認する必要がある。

ユーザーが選んだ統合方針は以下のとおり。

| 取り込む機能 | EmoAcademyでの扱い |
| --- | --- |
| 教材詳細 | 現行の学習カードから内容を確認する |
| 質問・先生の回答 | 質問と回答履歴をまとめて確認する |
| 提出 | 教材や課題に対する提出を扱う |
| 教師レポート | 教師が担当範囲の状況を確認する |
| 感情セッション | 学習中の分析結果をセッション単位で扱う |

旧Bootstrap風の見た目、旧ログイン画面、FastAPI認証、SQLiteは統合対象にしない。FastAPIという技術そのものを禁止する意味ではなく、表情分析APIと旧サイトの認証は別の役割として扱う。

別UIにも気に入った案はあったが、画像として候補を残すにとどめ、実装の本命は案Aにした。画面・操作の移植と、データ保存まで含む完成は区別する。

### 3.5 感情モニターとモデル処理

感情モニターを、ブラウザ内の簡易推定からモデルを用いる分析へ発展させた。端末のCPU性能への懸念から、Hugging FaceのCPU Spaceで重い推論を実行する方向を選んだ。

「enet_b0_8_va_mtl.pt」を使う構成を進め、過去に「model_loaded: true」を確認した。ただし、モデルを読み込めることと、認識精度が十分であることは別である。

認識精度が低く感じる問題について、カメラ条件、顔領域の切り出し、画像の前処理、API、推定ロジックを見直す作業を進めた。ブラー除去、リアルタイム表示、モニター開閉時のUI統一も調整した。

続いてDAISEEデータセットを使いたいという希望が加わった。既存モデルの実行と、DAISEEでの学習・評価は別工程であり、後者の完了はこの会話では確認できていない。

### 3.6 公開先とローカル確認の整理

GitHub、Vercel、Hugging Faceへの公開を進めつつ、URLの見た目、独自ドメインの必要性、処理をどこで行うかを整理した。ドメインはアクセスする住所であり、保存や計算性能そのものを提供するものではない。

GitHubアカウントの停止・復旧の話もあり、公開先の状態とローカル開発を分けて扱った。

ローカルサーバーの起動失敗に対して、起動バッチやHTMLをクリックして開くオフライン版を試した。しかし、オフライン版で左メニューやアイコンが変わったため、元のUIを維持する方針を再確認した。

### 3.7 Manabi Labのアイデアを吸収し、不要ファイルを整理

「knowledge-brain\online-learning-site」のManabi Labを起動し、科目ごとの進捗、次の学習行動、復習対象の絞り込み、週間の学習リズム表示を参考にした。

取り込んだ後、ユーザーから「ごちゃごちゃしているので、こういうものもある程度で持っておきたい」と修正が入った。現在のソースでは「参考機能：科目別の次アクションと学習リズム」という折りたたみ表示として保持している。

元サイトは有用な部分を取り込んだ後に削除する許可があり、大部分を削除した。過去の最終報告では約8MBの残骸があり、完全削除は未確認。これは現在の容量を再測定した結果ではない。

一方、「learning1-emotion_detection-main」と「Dataset_Autofocus」は残す指定がある。参考元と研究用データを混同して削除しない。

## 4. 技術構成と用語

| 要素 | 役割と意味 |
| --- | --- |
| Next.js／React | Web画面とその動作を作る仕組み。現在のpackage.jsonはNext.js 16.2.9、React 19.2.4 |
| TypeScript | データの種類を明示して、コードの不整合を検出しやすくする言語 |
| Git／GitHub | Gitは変更履歴の管理、GitHubはそのコードを共有・保管する場所 |
| Vercel | Webアプリをビルドし、インターネット上で公開するサービス |
| Supabase Auth | 登録・ログイン・認証情報を扱う機能 |
| Supabase Database | プロフィールや学習情報を表形式で保存するデータベース |
| Supabase Storage | PDFや画像などのファイルを保存する機能 |
| Hugging Face Spaces | モデルを動かすアプリやAPIの実行環境 |
| API | 画面とサーバーなど、別のプログラム同士がデータをやり取りする窓口 |
| 推論 | 学習済みモデルに画像などを入力し、予測を得ること |
| マイグレーション | データベースの表や権限の変更を、SQLファイルとして管理すること |
| RLS | データベースで、誰がどの行を読んだり変更したりできるかを制限する仕組み |

想定する役割分担は、学習サイトがVercel、認証・保存がSupabase、重い表情分析がHugging Face。Hugging Face上でサイト全体を動かす案も試したが、公開URLと計算処理の置き場所は別に選べる。

プロフィールのロールは学生・教師を区別する情報。画面で教師を選べることだけを根拠に、他の学生のデータへアクセスさせない。教師が確認できる担当範囲は権限として別に定義・検証する。

パスワードは閲覧用のファイルに保存するものではなく、認証基盤で管理する。プロフィールや進捗の表とは別に扱う。

## 6. 実験に向けて、これから決めること

現段階では「学習中の表情・状態と学習行動を扱える環境を作る」という方向がある。感情に応じてUIを自動変更する実験まで決定したわけではない。

次の項目は今後の設計事項であり、実装済み・決定済みの仕様ではない。

1. 何を推定するか：表情カテゴリ、Valence（快・不快の方向）、Arousal（活性の程度）、学習への関与などを区別する。
2. DAISEEを何に使うか：学習用、評価用、既存モデルとの比較用のどれにするかを決める。
3. 正解をどう定めるか：モデルの出力を本人の感情の事実とせず、自己報告や評価ラベルとの対応を考える。
4. 何を測るか：誤答・所要時間・学習継続、推定精度、応答の遅延、モニターが邪魔かどうかなどから選ぶ。
5. どう比較するか：モニターの有無、表示方法、モデルなど、比較対象を明確にする。
6. 何を保存するか：学習セッションID、時刻、学習行動、推定値、モデルの版などを検討する。映像送信・保存の有無と利用者への説明も実際の構成に合わせる。

DAISEEはデータセットであり、そのままモデルの代わりに置いて動かすものではない。学習した重みも、ファイル名や拡張子が合うだけでは使えず、モデル構造、入力の前処理、出力の順序を推論側に合わせる必要がある。

既存のDAISEEメモにある読み込み・出力形式の説明は実装時の想定として扱い、任意の重みファイルとの互換性が確認済みとは解釈しない。

## 7. 次に進める順番と完了の目安

### 優先1：現行UIで学習機能を一通り使う

教材を開く、質問する、教師が回答する、提出する、レポートで確認する、という流れを点検する。重複した導線や日英混在も確認する。見た目を大きく変える場合は画像で比較して確認する。

完了の目安：学生と教師の役割で、想定した操作が途中で行き止まりにならない。

### 優先2：保存と権限を確認する

既存のSQL適用状況、フロント側の保存処理、Supabaseの実データを照合する。未適用と決めつけてSQLを再実行しない。デモ値や端末内だけの保存を、サーバー保存と区別する。

完了の目安：再ログイン・別端末でも本人のデータが復元され、他人のデータを権限なく閲覧・変更できない。

### 優先3：感情分析の入力から表示までを検証する

顔画像の切り出し・サイズ・正規化、モデル出力のラベル対応、推論の頻度と遅延、失敗時の表示を確認する。その後にDAISEEを用いる学習・評価へ進む。

完了の目安：同じ入力に対する結果を追跡でき、モデルの読み込み成功と精度評価を別々に説明できる。

### 優先4：実験計画に落とす

研究上の問い、比較条件、参加者、評価指標、取得データを決める。参考にした論文と、実際に採用した設計要素の対応も記録する。会話では複数論文の参照を依頼しているが、本書では個別論文への対応関係を検証していない。
